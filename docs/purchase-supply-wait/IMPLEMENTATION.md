# توضيح انتظار التوريد — 2026-11-08

## النطاق

إضافة معلومات اختيارية للصنف بانتظار الشراء، دون انتقال حالة أو إجراء شراء/دفع أو تغيير اعتماد أو مبلغ أو موعد احتياج أو ارتباط ببلاغ/PMV2. لم تتغير دوال الشراء والتسعير والاعتماد أو استعلاماتها أو شكل استجاباتها؛ تعرض الإضافة بقراءة مستقلة.

## ما نُفّذ

- زر أزرق «توضيح انتظار التوريد»، بتأثير ضغط وتركيز لوحة مفاتيح. يفتح خيارَي «بانتظار توفير الصنف» و«قيد التجهيز»، ثم نافذة بتاريخ من التقويم وتفاصيل السبب وزر حفظ. كلا الحقلين مطلوبان عند استخدام الإضافة؛ تركها بلا استخدام لا يمنع أي إجراء أصلي.
- جدول مستقل `purchase_item_supply_wait` بسجل واحد لكل صنف،12عمودًا، ورقم مراجعة للتعارض. يحفظ صاحب الإدخال ووقته الأول واسم آخر معدل ووقته. لا backfill. مفتاح الصنف يحذف التوضيح فقط عند حذف الصنف، دون منع مسارات الحذف القديمة أو تعديلها.
- وقت الخادم UTC صريح، والعرض بتوقيت الرياض. مهلة ساعتين من أول حفظ لا تتجدد بالتعديل؛ يراجعها الخادم مرة أخرى في شرط UPDATE نفسه. يحافظ الأدمن/المالك على حق العرض والتعديل بلا مهلة.
- قبل المهلة يرى البيانات الأدمن/المالك والمندوب الحالي المسند إليه الصنف. بعد المهلة تُعرض أيضًا لمنشئ الطلب والمراجع الفعلي للصنف، دون منحة تعديل لهما. يستخدم مراجع الصنف الموجّه، ويرجع لمراجع رأس الطلب فقط للصنف القديم غير الموجّه. لا تكفي صفة «مدير/مراجع» وحدها.
- الإضافة متاحة في بطاقات المندوب، متابعة أصناف المنشئ، متابعة التوريد، تفاصيل بنود الطلب، وبطاقات دورة الشراء القائمة. يبقى التوضيح ظاهرًا بعد الشراء؛ إنشاء توضيح جديد يبدأ من حالة بانتظار الشراء، والتعديل على الموجود يخضع للمهلة نفسها.

## حدود الخادم والصلاحيات

- RPC مستقل `purchaseSupplyWait.list/save`، بمنحة قراءة صريحة لأدوار الأعمال المقيدة وحارس قدرة مركزي للكتابة: مندوب/مسئول مناديب/أدمن/مالك فقط. يراجع كل طلب هوية الحساب الحالية ونشاطه ودوره من DB، وملكية/إسناد الصنف وعلاقته الصحيحة بطلبه، إضافة إلى نطاق قراءة PO الحالي ومرشح بنوده.
- القراءة دفعات حتى500صنف لكل RPC، بآباء مميزين وحارس نطاق واحد؛ لا استعلام لكل بطاقة. هوية المستخدم ودوره جزء من مفتاح الاستعلام وتُطابقان مع الهوية الفعلية؛ لا يُعاد استخدام إسقاط أدمن قديم لمستخدم/دور آخر.
- لا يرسل API السبب أو الموعد أو اسم صاحب الإدخال أو وقت حفظه إلى المنشئ/المراجع قبل الساعتين. لا تحفظ المعلومة في تعليقات عامة أو إشعارات أو PDF؛ سجل التدقيق يحفظ المرجع والمراجعة فقط. تتجدد القراءة دوريًا كل30ثانية وعند عودة التركيز، دون مجدول أو إشعار أو تعديل مؤشرات التأخير الحالية.
- الحفظ في معاملة مستقلة: قفل المصدر الحالي والتوضيح، مراجعة النسخة والمهلة، كتابة جدول الإضافة وسجل التدقيق فقط. فشل التدقيق أو انتهاء المهلة/التعارض يلغي المعاملة. لا حذف أو إعادة إنشاء للتوضيح لتجديد المهلة.
- غياب الجدول الاختياري نفسه قبل الترحيل يخفي الإضافة ويحفظ استعمال الشاشة القديم. أخطاء الاتصال أو مخطط مختلف لا تتحول إلى نجاح فارغ؛ تعرض الإضافة خطأ قراءة مستقلًا.

## الملفات

- `shared/purchase-supply-wait.ts`: المدخلات والمهلة والقدرات والـDTO وتقسيم القراءات.
- `server/services/purchase-supply-wait.ts` و`supply-wait.router.ts`: القراءة والحفظ المستقلان. الربط فقط في فهرس الراوتر وحارس القدرة وقائمة قراءات أدوار الأعمال.
- `SupplyWaitExplanation.tsx` و`purchaseSupplyWait.ts`: الواجهة وترجماتها الثلاث. ربط محدود بصفحات PurchaseOrders/PurchaseOrderDetail/PurchaseCycle ومكوّن DelegateSupplyRows؛ لا إعادة تصميمها.
- `drizzle/schema.ts`: تعريف الجدول الإضافي فقط، دون أعمدة جديدة في رأس أو أصناف PO.
- `01_copycmms2.sql` ثم `02_cmms.sql`: أوامر يطبقها المستخدم يدويًا. الفحص أولًا؛ CREATEعند غياب الجدول فقط. لا تغيير.env أو مفتاح تفعيل جديد.
